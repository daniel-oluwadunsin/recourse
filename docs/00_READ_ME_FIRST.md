# Recourse — Final MVP Engineering Handoff

## Purpose

This bundle is the implementation source of truth for **Recourse**.

Recourse is a general-purpose autonomous case-intelligence product for people facing adverse or consequential decisions from institutions, platforms, companies, schools, governments, insurers, employers, financial services, marketplaces, and other organizations.

The system must **not hardcode domains**. A user may bring essentially any case.

Examples are only examples:

- a marketplace seller suspension;
- a university scholarship termination;
- a payment account restriction;
- an insurance denial;
- a creator-account suspension;
- a government-benefit decision;
- an employment or disciplinary decision;
- a visa/immigration decision;
- a tax decision;
- a telecom dispute;
- a housing decision;
- a gig-worker deactivation;
- an academic decision;
- an unfamiliar case that was never explicitly anticipated by the codebase.

The common abstraction is:

> **A user received a consequential decision and wants help understanding it, researching the current process, organizing evidence, preparing a response, and continuing the case after the institution replies.**

## Final MVP stack

Keep the product deliberately simple:

- **Frontend:** Next.js + TypeScript
- **Backend:** NestJS + TypeScript
- **Database:** MongoDB Atlas
- **AI:** Google Gemini API
- **Current default AI model:** `gemini-3.7-flash` unless current official docs or account availability require a better free-tier-compatible model
- **Live web research:** Tavily Search + Extract
- **Evidence storage:** Cloudinary
- **UI:** Tailwind CSS + shadcn/ui
- **Forms:** React Hook Form + Zod
- **Server state:** TanStack Query
- **Testing:** unit/integration tests + Playwright E2E
- **Package management:** pnpm workspaces

Do not introduce extra infrastructure without a demonstrated need.

## Critical product boundary

**Recourse never submits the case for the user in the MVP.**

Recourse researches, analyzes, prepares and assists.

The user decides what they want to do and performs the external action themselves.

When a case is ready, Recourse offers user-controlled tools:

- **Draft appeal/response email**
- **Generate formal letter**
- **Ask Recourse** — case-aware intelligence for portal/form questions or any question about the case

Examples:

> "The portal asks why I think this decision is wrong. What should I write?"

> "What documents should I attach?"

> "They ask what changed since the violation. How should I answer based on my evidence?"

Recourse answers using the case, evidence and verified procedure.

After the user acts externally, they click:

> **I've submitted**

Recourse then asks what was actually submitted and changes the case to waiting for a response.

When a response arrives, the user returns and selects:

> **I received a response**

They upload/paste it, and Recourse re-analyzes the same persistent case and recommends the next legitimate step.

## Three truths Recourse must keep separate

### 1. Case truth

What user evidence establishes.

### 2. Procedural truth

What current retrieved sources establish about the institution/process.

### 3. User choice

What the user decides to do.

Recourse does not confuse these.

## Product behavior when important information is missing

If Recourse cannot reliably identify an essential fact such as the institution or enough context to research the process:

1. ask the user one focused question;
2. set the case to `NEEDS_INFO`;
3. wait;
4. continue automatically after the user supplies the answer.

Do not guess.

## Product behavior when no formal process is verified

Say so plainly.

The user may still:

- draft an email;
- generate a formal letter;
- ask Recourse for help understanding or communicating about the case.

Do not invent an official appeal route.

## Conflicting sources — MVP behavior

Do **not** overwhelm the user with source conflicts.

Internally rank sources and choose the most credible applicable procedure using factors such as:

1. authority;
2. specificity to the user's exact situation;
3. jurisdiction match;
4. recency/currentness.

Retain provenance internally.

If uncertainty is too severe to make a responsible choice, say the procedure could not be verified instead of inventing certainty.

## Universal domain support

Domain handling must be **model/research driven, not hardcoded**.

Do not implement:

```ts
if (domain === "amazon") ...
if (domain === "insurance") ...
```

The system should extract generic case concepts and research the user's actual institution and decision.

High-stakes cases may receive a plain-language suggestion to involve qualified professional help, but Recourse can still organize the case, analyze evidence and retrieve official procedural information.

## UX requirement

The landing page **and the entire authenticated product** should feel like a premium **Awwwards-caliber digital product**:

- highly polished;
- editorial;
- visually distinctive;
- refined typography;
- exceptional spacing;
- tasteful motion;
- smooth transitions;
- strong information hierarchy;
- sophisticated use of depth, glass, grain, gradients or other design language only if consistent with `design.md`;
- no generic SaaS-dashboard look;
- no generic AI-chatbot look.

However:

> Beauty must never make the case workflow confusing.

The UI must remain immediately usable by a stressed, non-technical user.

`design.md` is the visual authority.

## Rigorous visual validation is mandatory

When implementation is complete, Codex must use Playwright/browser inspection to walk through **every meaningful flow and state**, capture/inspect screens at multiple viewport sizes, and fix visual or usability issues before declaring completion.

This is not optional.

## Existing `.env`

The repository was previously built and then deleted except for existing files such as `.env`.

Codex must:

1. inspect the existing `.env`;
2. never print secret values;
3. map existing variables to the final implementation;
4. preserve values that are still required;
5. remove variables for integrations that are no longer used;
6. add missing variable names only when required;
7. update `.env.example`;
8. explain which stale entries were removed without revealing values.

Likely obsolete integrations include Groq, R2, Voyage/vector search, Redis or other remnants from earlier builds — but Codex must inspect rather than blindly delete by name.

## Provider/privacy note

The current Gemini Developer API pricing documentation states that free-tier submitted content may be used to improve Google's products, while paid-tier content is not.

This is important because Recourse can handle sensitive documents.

For the MVP:

- Codex must document this clearly;
- do not hide the provider policy;
- use non-sensitive fixture data for public demos/testing;
- provide a concise user-facing notice before sending real uploaded content to Gemini if the product will accept real users;
- do not claim zero-retention/privacy guarantees that the free Gemini tier does not provide.

Official reference:
https://ai.google.dev/gemini-api/docs/pricing

## Definition of done

The app is not done because it compiles.

It is done when a non-technical person can:

1. create an account;
2. bring an arbitrary case;
3. upload/paste the decision;
4. answer a missing-information question if Recourse needs one;
5. understand what Recourse thinks happened;
6. see current sourced procedural guidance;
7. upload evidence;
8. understand useful and missing evidence;
9. ask case-aware questions;
10. generate an appeal/response email;
11. generate a formal letter;
12. confirm what they actually submitted;
13. later add the response;
14. see Recourse continue/replan the case;
15. complete the experience on desktop and mobile without technical jargon.
